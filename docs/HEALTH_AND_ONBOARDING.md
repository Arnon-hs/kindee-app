# Онбординг, часы и локальные сборки

Состояние реализации: локальная разработка. Production API отсутствует; публичный клиент и исходники доступны отдельно. Связь с физическими устройствами еще не проверена.

## Сценарий пользователя

1. Администратор локальной установки создает аккаунт: `docker compose exec api php artisan kindee:provision you@example.test`. Команда `kindee:token you@example.test` выпускает личный токен на 30 дней. Токен вводится в приложении и хранится только в памяти текущего сеанса. Публичной регистрации и OAuth провайдеров в этой версии нет.
2. После входа впервые открывается обязательный онбординг: наблюдение / поддержание / снижение / набор веса; рост, измеренный вес, необязательный желаемый вес, обычная активность. Согласие на сохранение параметров обязательно. Повторная отправка того же исходного веса не создает дубликат измерения.
3. Пользователь выбирает Health Connect / Apple Health / прямой импорт Wear OS / неизвестные часы / подключить позже. Для завершения с выбранным поддерживаемым источником нужны сегодняшние данные, прочитанные не более 2 часов назад; выбор названия приложения сам по себе не подтверждает связь. Пропуск явно сохраняется; он никогда не означает подключение. Поля можно изменить через Настройки → Настроить цель и часы.
4. Часы сначала подключаются в официальном приложении производителя. Для импорта через телефон производитель должен действительно экспортировать записи в Apple Health или Health Connect. Разрешение, отсутствие записей и неподдерживаемая передача различаются в интерфейсе. Собственных OAuth/API интеграций с Zepp, Garmin, Fitbit и другими производителями здесь нет.
5. В нативной сборке пользователь дает согласие на передачу KinDee, проходит системный запрос доступа, выбирает одно приложение-источник и запускает ручную синхронизацию. Доступны активная энергия и шаги, если их действительно отдает выбранный источник. Наличие разрешения само по себе не создает показаний.
6. Дневные цели КБЖУ задаются отдельно в настройках. Активность показывается рядом с питанием. Автоматического увеличения пищевого бюджета, назначения дефицита или перевода ккал в сброшенные килограммы нет. Изменение веса считается только по измерениям.

## Совместимость и границы

| Клиент / устройство | Реализация | Проверка |
| --- | --- | --- |
| Vue PWA, Safari/Chrome/desktop | Онбординг, приватный API, просмотр импортов, manifest/SW, кеш только общедоступных рецептов | TypeScript, сборка и автоматические тесты; ручная браузерная проверка не выполнена |
| Android-телефон | Capacitor 7, Health Connect 1.1.0, выбор data origin, активная энергия/шаги, ручная отправка в Laravel | Kotlin компилируется; установка и сенсоры требуют реального устройства |
| Wear OS 3+ | Отдельный APK, Health Services, дневные шаги и общий расход, отправка на парный Android через Wearable MessageClient | Kotlin компилируется; поддержка датчиков зависит от модели |
| iPhone | Capacitor, HealthKit: запрос чтения, источники, активная энергия/шаги | Исходники и Xcode-проект; компиляция и подпись в этой Linux-среде невозможны |
| Apple Watch (watchOS 9+) | SwiftUI-клиент чтения HealthKit для показа дневной активности; iPhone импортирует выбранный источник через HealthKit | Исходники и XcodeGen target; сборка и физическая синхронизация не проверены |
| Часы на фотографиях | Внешне похожи на Amazfit; точная модель не подтверждена | Нельзя обещать устанавливаемую сборку или универсальный Bluetooth-протокол |

Предположение о GTS 2 mini не является идентификацией. Если это GTS 2 mini (A2018), официальная документация Zepp относит модель к **Non-Zepp OS Devices**: Wear OS APK и Zepp OS mini-app на нее не устанавливаются. Возможен только маршрут через поддерживаемый официальный экспорт данных; наличие и состав экспорта конкретных часов не проверены. Для других Amazfit/других проприетарных ОС также сначала требуется подтвержденная модель и документированный SDK/API.

PWA не читает HealthKit или Health Connect напрямую и не реализует системные WidgetKit/Android App Widgets. Подключение часов к официальному приложению не означает доступ KinDee к их данным.

## Локальная проверка Android

Требуются JDK 21, Android SDK Platform 36, build tools, Node/npm. В `apps/web`: `npm ci`, затем `JAVA_HOME=... ANDROID_HOME=... npm run build:android`. Скрипт собирает **debug** APK для телефона и Wear OS. Release-подпись и Play Store release не подготовлены. Health Connect требует совместимого телефона и установленного/встроенного сервиса; обычно Android 9+ со standalone Health Connect либо Android 14+ со встроенным сервисом.

1. Запусти Core через Docker Compose и миграции. `http://localhost:8080` — адрес браузера на компьютере, не телефона.
2. Для USB-теста телефона включи USB debugging и выполни `adb reverse tcp:8080 tcp:8080`. Тогда в KinDee укажи `http://127.0.0.1:8080`. Для Wi-Fi используй адрес компьютера вида `http://192.168.1.10:8080`, доступный телефону. Не публикуй локальный dev API в Интернет.
3. Установи телефонный debug APK: `adb install -r app-debug.apk`. Для Wear OS подключи часы через Android Studio/ADB и отдельно установи `wear-debug.apk`. Один applicationId используется для связи парных устройств; телефон и часы должны иметь сборки с одинаковым сертификатом.
4. Введи адрес API и персональный токен, пройди онбординг. Health Connect: предварительно проверь реальные записи от официального приложения часов, дай разрешения, выбери источник, нажми синхронизацию.
5. Прямой тест Wear OS: держи KinDee открытым на обоих устройствах. На часах нажми `Allow & read`, дождись настоящих показаний, затем `Send to phone`; на телефоне после согласия нажми импорт Wear OS. Часовой пояс часов должен совпадать с профилем. Фоновый сбор и надежная фоновая доставка не реализованы.
6. Wear OS `CALORIES_DAILY` включает основной обмен: сохраняется только в `total_energy_kcal`, а `active_calories_kcal` остается null. Эти показания не увеличивают пищевую цель.

Локальная debug-сборка разрешает HTTP к приватным IP/localhost для теста. Обычная release-конфигурация требует HTTPS. Адрес API и токен не встроены в APK; native API URL проверяется, логин и данные находятся в памяти. Native WebView использует упакованные файлы, не регистрирует SW. Разрешения ОС сохраняются отдельно от сеанса KinDee.

## iPhone и Apple Watch

В Linux нет Xcode, Apple SDK, provisioning и пользовательской Apple Developer team. Поэтому IPA, watchOS binary и TestFlight-ссылка не выдаются и не обозначаются как собранные.

На Mac установи Xcode, XcodeGen, CocoaPods, Node, затем в `apps/web` выполни `npm ci` и `npm run build:apple`. Скрипт обновляет Vue bundle, копирует iOS assets, генерирует iPhone + Watch targets из `ios/App/project.yml`, устанавливает Pods и пытается скомпилировать unsigned simulator builds. Этот путь еще должен быть выполнен на macOS: Linux-проверка XML/YAML не заменяет Swift/Xcode-компиляцию.

Для физического теста открой `ios/App/App.xcworkspace`, выбери свою Team для обоих targets, включи HealthKit capability/entitlements, проверь уникальные bundle IDs для своего provisioning, выбери парные iPhone/Apple Watch и установи Debug из Xcode. HealthKit возвращает завершение запроса доступа, но намеренно скрывает разрешение на чтение: отсутствие данных может означать отказ или отсутствие записей. KinDee показывает неизвестное значение, не нулевую активность. Отзыв HealthKit выполняется пользователем в настройках телефона.

PWA без HealthKit можно установить отдельно: iPhone Safari → Поделиться → На экран "Домой"; Android Chrome → Установить приложение / Добавить на главный экран. Нужен HTTPS (или localhost самого устройства). Для локального теста на другом телефоне потребуется доверенный локальный HTTPS сертификат/туннель; обычный LAN HTTP не обеспечивает Service Worker. Встроенный публичный демо-сайт содержит только примерные данные и не подключается к локальному API автоматически.

## Данные, API и приватность

`GET/PUT /api/v1/onboarding`; `GET/DELETE /api/v1/health`; `POST /api/v1/health/sync`; health summary также входит в dashboard. Все маршруты требуют токен, отвечают `private, no-store`, не попадают в SW cache. Контракт — `docs/openapi.yaml`.

Импорты хранятся в PostgreSQL у владельца аккаунта. Уникальность — account/provider/origin/local date/timezone. Повторная синхронизация заменяет дневной накопительный снимок; более старый запрос не перезаписывает новый. Выбирается один источник; источники и устройства не суммируются. Импорты за другой часовой пояс профиля и будущие даты отклоняются. Импорты старше 90 дней не принимаются. Текущий импорт старше 2 часов помечается устаревшим. `collected_at` означает время чтения/получения клиентом, а не гарантию свежести каждой записи производителя.

Происхождение — `client_reported`, без аппаратной аттестации. Эти API предназначены для учета питания, не для антифрода или клинических решений. Удаление подключения удаляет все health imports аккаунта; дневник еды, исходные параметры и измерения веса остаются отдельными данными. Android-приложение также пытается отозвать Health Connect permissions; в Apple Health отзыв делается через системные настройки. Автоматической синхронизации/экспорта между рынками и интеграций GrabFood/LINE MAN эта функция не добавляет.
